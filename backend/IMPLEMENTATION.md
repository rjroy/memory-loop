# Current backend implementation notes

These are descriptions of the current implementation, not a grant of authority over product behavior or an approved future filesystem policy. They may change as the application evolves. See [API.md](API.md) for the interface and [ARCHITECTURE.md](../ARCHITECTURE.md) for work boundaries. In particular, no choice to follow or reject links is established here as a user-approved requirement.

## Filesystem mechanics and limits

The shared filesystem foundation canonicalizes the configured root and checks its identity, validates descendant components and containment, and currently rejects descendant symbolic links and Windows directory junctions. The configured root and its ancestors can resolve through links. A detected root replacement makes subsequent access unavailable. Checked ordinary paths are not reservations or a race-proof pathname sandbox against hostile local processes. The OS and local account control access permissions; the service does not enforce owner-only storage or inspect ACLs.

An opened file handle pins the file being read, not the pathname leading to it. File and media streams close their handles on completion or cancellation. Hardlinked regular files can be read; direct write/append handles reject hardlinks. Saving replaces the selected pathname and leaves other aliases on the original bytes. A tree is not a transactional snapshot, and external namespace changes can cause unavailable or conflict results.

Memory Loop serializes its own mutations, checks for observed collisions and uses exclusive creates. Moves use checked source/destination paths and ordinary rename, with no atomic no-overwrite guarantee against external writers; cross-device moves are refused. Recall no longer uses the Linux/glibc Bun FFI rename adapter. Replacement content uses an exclusively created temporary file and file flush before publication; directory metadata is flushed where supported, not on Windows. Outcomes after publication can be uncertain. These checks are not filesystem compare-and-swap or identical power-loss durability across platforms. New names are checked for Windows compatibility on both platforms; existing host-valid names are not hidden solely for being nonportable. Native Windows execution remains unverified; see the [operator guide](../README.md#operator-guide).

## Search and transport mechanics

Current matching uses `fuzzysort` 4.0.2 with prepared targets. Content detection uses `file-type` 22.3.0, which requires Node 22 or later under Node.

Versions use the existing opened reader's secret-scoped file-stat token (identity, size and modification/change times), not the Markdown save revision or a public content hash. Both search and context verify descriptor versions before/after reads and reopen the current vault-relative path to check that it still names that version. Tokens from a different reader/daemon lifetime are stale. Context checks that the requested target still matches the supplied normalized query; it never returns an unverified excerpt after a deadline. It may stop reading after the needed excerpt, rather than decoding the entire remainder of a large file. As with other vault operations, this is not filesystem compare-and-swap against hostile local writers.

The Next boundary allows up to five seconds to receive/parse the bounded JSON request, then uses a separate 35-second daemon-response budget for both search and context. Daemon work has a 30-second deadline from admission; metadata helpers and global startup deadlines are unchanged. At most two nonempty search/context operations run concurrently across the process, with no waiting queue; excess requests fail with `503 search_unavailable`. Each scan processes files sequentially in bounded read chunks with real event-loop yields. There is no 10,000-entry vault rejection. Cancellation/disconnect propagates through the private HTTP transport and closes request-owned file/directory resources; reader shutdown also cancels its searches. Repeating or cancelling a search does not mutate files.

For uploads, Next uses a 15-second limit-fetch deadline and a 60-second idle deadline reset by byte progress. The daemon also bounds upload-body idle time. Next retains Node's five-minute absolute request-receive timeout, so progressing uploads can still time out. The upload destination is checked without following descendant links. A complete upload is written to an exclusively created hidden temporary file, flushed and published through the mutation queue after checking the destination. Interrupted partial uploads are cleaned up when the checked namespace remains available. External directory relocation or replacement can leave a hidden temporary file behind rather than allow deletion through an untrusted path; that residue alone does not establish publication.
