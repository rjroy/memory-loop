# Think execution and current-conversation reconnect

## Recommended direction

Keep **private Tailscale Serve → Node Next presentation/BFF → Bun/Hono daemon → separate local OpenCode service**. The daemon accepts commands and monitors execution independently of every browser. Next authenticates and projects a small application API; it does not run agents. OpenCode owns models, tools, permissions, compaction, and native session history.

Use the official **`@opencode/client@2.2.2` Promise client**, not the embedded SDK or CLI-output scraping. Version-matched official source and the published client are available. Their experimental session log is the preferred replay/follow foundation, subject to the mandatory isolated capability gate below. Do not silently replace a failed gate with live-only streaming or a home-built agent runtime.

Give each conversation a stable opaque identity, each Send a daemon-owned operation/run identity, and every client command an idempotency identity. Recover the **current** conversation through its URL and an authoritative daemon snapshot, then follow ordered application updates. New chat allocates a different conversation without stopping or abandoning monitoring of earlier work. There is no conversation list or previous-chat picker in Think; that future interface belongs on Ground.

This is the design draft for `memory-loop-42j.1`, not implementation authorization, a finished integration, or approval of adjacent designs. `42j.2` owns vault transcripts, `42j.3` configuration/tool policy, and `42j.4` the Impeccable experience. Only their necessary seams are specified here.

## Ownership and identity

### Service boundaries

- **Browser:** current-conversation pointer, editable volatile draft, presentation/focus/scroll, and rendering the daemon's state. It never owns a run or infers whether tools finished.
- **Next BFF:** existing web request policy, fixed-route forwarding, fresh server credentials, validation/projection of the application protocol, and bounded connection resources. No operation registry, transcript writes, OpenCode credentials, or agent configuration here.
- **Bun/Hono daemon:** command receipts, conversation/run association, per-conversation admission/Stop coordination, normalized state and revisions, upstream subscriptions/reconciliation, and the transcript-writer seam. Inject these services into the listener-free app; shutdown closes its observers explicitly.
- **OpenCode:** authoritative admitted inputs, agent execution/history, provider access, tools and permission evaluation. Only Memory Loop-created sessions are attached. Reusing the user's configuration/service does not import or adopt TUI conversations.

Prefer operator-managed OpenCode service lifecycle. The daemon uses `Service.discover` with an exact approved version and `Service.headers` server-side, then checks `server.info`; it does not call `ensure`, replace an incompatible service, or stop a shared service on shutdown. [The matched service implementation][service-source] confirms discovery does not launch a process and that ensure/stop can manage processes. An unavailable/incompatible service makes Think unavailable without breaking Recall. An upgrade requires re-running the gate; “any 2.x” is not the compatibility policy.

`42j.3` must supply the selected service registration and explicit canonical working-directory/location. Do not inherit the Memory Loop launch cwd accidentally: the [session handler][handler-source] otherwise defaults creation to the service cwd. Configuration reuse covers supported server/project agents, models, skills and plugins after verification; TUI-only [`cli.json` settings][cli-config] are not server configuration. Do not copy private config/auth into Memory Loop or assume every TUI plugin has a usable web interaction.

### Three stable IDs, not transport identities

| Identity | Allocation and lifetime |
| --- | --- |
| `conversationId` | Random opaque UUID allocated before the create request. Stable across current-chat reconnect/reload and independent of a Navigation API entry key, tab component, HTTP connection, or run. The daemon deterministically derives a valid caller-supplied OpenCode session ID and writes a Memory Loop ownership marker plus this ID in that new session's metadata. The browser receives only the application identity. |
| `runId` | Daemon UUID allocated once when registering a Send. Represents one application operation, not one model response, tool call, retry, or compaction. Returned on receipt lookup and all relevant state updates; stored in the admitted prompt's metadata for later correlation. A service-originated background continuation gets its own activity/run record, not a fabricated Send receipt. |
| `clientCommandId` | Browser UUID allocated once per create/Send/Stop/decision reply. Reused only to query or repeat the **same immutable command**. For Send the daemon derives a stable valid OpenCode prompt ID from it. Request IDs remain separate diagnostics. |

The daemon records command kind, conversation/target run, immutable payload/digest, receipt, and upstream IDs **before dispatching**. Repeated browser delivery returns that receipt, without another upstream dispatch. Same ID with another payload, kind, or target is a conflict, even though OpenCode might accept “first wins.” Receipts are checked before busy-state rejection. Keep accepted, uncertain and cancelled receipts throughout the daemon lifetime; a stopped input must never be resurrected by a late retry.

For this browser-disconnect layer, the daemon's command registry and live projection may be resident memory. OpenCode persists session identity, ownership metadata, prompt metadata and native history. That is enough to avoid a disposable identity scheme; future Ground listing/reconstruction can use the same identities and public session resources. It is **not** a commitment to a new application database or to restart recovery now. Do not export runtime receipts or raw tool payloads to the vault as a substitute for the `42j.2` design.

Give each daemon lifetime an `epoch` and each conversation projection a monotonically increasing `revision`. Upstream session sequence, daemon revision, message/part identity and browser navigation identity have different meanings; do not interchange them. An unknown epoch/record after a daemon restart is an explicit continuity-unavailable state, never proof that the conversation is empty or permission to recreate/resend it.

## Current conversation and New chat

Use **`/think?conversation=<opaque-id>`** as the canonical current-chat URL. A single per-tab `sessionStorage` pointer holds only that ID for return after reloading another app tab; no messages, drafts, credentials, command outbox, or history list go into browser storage. Explicit URL identity wins. Keep this Think-specific pointer separate from Recall's in-memory presentation snapshots and retain the public Next/Navigation API navigation discipline.

- Initial bare Think with no pointer allocates an ID, replaces the current URL, and explicitly creates the conversation with a stable create command. Creation is itself daemon-owned and idempotent. A lost create response is reconciled by ID, not followed by another randomly identified session.
- An existing current URL/pointer causes lookup/reconnect, **not create**. Unknown/malformed/unavailable IDs have distinct errors. Verify the ownership marker; never attach an arbitrary existing OpenCode/TUI session because an ID was supplied.
- New chat allocates a different ID and replaces the current pointer/Think URL rather than adding an old-chat browsing affordance. It never sends Stop, deletes/archives the old conversation, or releases its daemon monitor. Failed new creation does not change the old run's fate. It must not copy the old draft into a different conversation.
- Moving to Ground/Capture/Recall unmounts only the view/watch. Returning to Think uses the current pointer. The daemon retains all accepted-run monitoring without browser subscribers, including pending decisions and late background-tool output. No subscriber reference count may cancel or retire that work.

| Event | Proposed guarantee |
| --- | --- |
| Connection returns, app refocuses, or state is refreshed | Same conversation; authoritative resync then follow. Do not resend a prompt. Volatile draft remains. |
| SPA tab navigation and return | Same current pointer and draft; run never depended on the mounted view. |
| Hard reload on Think | URL restores the current identity; messages/status/decisions come from the living daemon. Unsent draft is lost. This differs from a state refresh. |
| Hard reload on another app tab | Per-tab ID pointer supports returning to the current Think conversation; the draft is still lost. |
| Browser closes | Accepted execution/daemon monitoring continue. Reopening the retained full URL can reconnect while the daemon lives. A fresh bare browser context is not promised to rediscover a chat. |
| New chat | Fresh identity and empty draft; old runs continue. There is no promised return control in this layer. |
| Daemon/OpenCode process restart or crash | Not this layer's execution/durability guarantee; see failure scope below. |

The URL/pointer is current-conversation recovery, not a prior-chat selection interface. It also supplies the stable opening seam a later Ground entry needs. It is not a bearer capability: every API read/control still passes authentication and ownership checks. Session storage unavailability must not prevent URL-based reconnect; report the narrower off-Think reload behavior rather than introducing a content-storage fallback.

## Commands and asynchronous admission

Proposed Memory Loop routes below are **new application contracts**, not names of existing routes or a passthrough OpenCode API. Use explicit Node Route Handlers and matching authenticated Hono routes:

| Route | Purpose |
| --- | --- |
| `POST /api/think/conversations` | Register create with supplied `conversationId` and `clientCommandId`. |
| `GET /api/think/conversations/:id` | Authoritative normalized snapshot/current availability. |
| `GET /api/think/conversations/:id/messages?cursor=<opaque>` | Page message/part manifests within this conversation; body references retrieve the full values. |
| `GET /api/think/conversations/:id/content/:contentId?generation=<opaque>&through=<byte>&offset=<byte>[&transfer=<opaque>]` | Read the next bounded chunk of an identified immutable content prefix, with authentication on every request. |
| `POST /api/think/conversations/:id/messages` | Register immutable text Send and return its receipt/run ID. |
| `GET /api/think/conversations/:id/commands/:commandId` | Resolve lost acknowledgements without sending again. |
| `POST /api/think/conversations/:id/runs/:runId/stop` | Register explicit Stop for that run, with its own command ID. |
| `GET /api/think/conversations/:id/events` | Snapshot-first SSE followed by ordered application updates. |
| `POST /api/think/conversations/:id/decisions/:decisionId/reply` | Reply to a currently pending typed permission/form decision. |

History pages contain chronologically ordered message/part manifests, stable IDs, the conversation ID/epoch, body references, and opaque continuation cursors; consumers merge by ID, not array position. Bound each encoded manifest page by bytes as well as item count; a cursor can continue a single message's part list. Snapshot history anchors and cursor validation belong to the daemon, not a browser-supplied upstream URL. This is not Ground's future conversation-list API. Full user/AI text remains retrievable through the content-chunk contract below, including a single oversized part; a reference is not a summary or truncation. Do not use OpenCode's post-compaction context endpoint as the full conversation. Control state and content descriptors stay resident; message bodies use a bounded-memory, private spill-file path rather than requiring every open/old body to remain in RAM. Bounding buffers/working memory must not cap conversation turns, discard native history, or stop an unselected run.

1. Validate/authenticate, record the command, reserve the per-conversation admission slot and schedule daemon-owned work. A quick **202** means “registered by the living daemon,” not “the model has completed” or “crash-durably saved.” Include command/run IDs and current admission state. Do not hold the web request open for generation.
2. The daemon makes the versioned prompt call with the fixed session ID, immutable text, stable prompt `id`, and run/command metadata. OpenCode's returned inbox item or matching durable admission event advances it to **agent-admitted**. Preserve that distinction in state, even if the usual UI transition is fast. Preserve the original user submission separately from any plugin-prepared prompt expansion; do not misattribute injected skill/instruction text as something the user typed or export raw preparation metadata to the browser.
3. A timed-out/lost browser response is **unconfirmed**, not rejection. Query its command receipt and conversation snapshot. Repeating the identical application command is safe because it only reads the already-registered receipt; Next does not retry POSTs automatically.
4. A daemon-to-OpenCode transport failure can leave upstream admission uncertain. Reconcile using the same prompt ID in durable log, inbox, and projected message lookup. A single absent lookup is not proof of non-admission while the first request may still be preparing. Do not generate another prompt ID or automatically retry an already admitted/cancelled input. The initial implementation should not re-dispatch an ambiguous upstream prompt; retain its task/result if still obtainable, keep checking authoritative state with bounded backoff, and expose uncertainty if it cannot be resolved. New chat remains possible without pretending the old request failed.
5. Definitive validated rejection can restore a Send attempt to the composer for explicit correction/retry with a **new** command. A fresh command is a deliberate new user action, not transport recovery. Plugin preparation and arbitrary tool effects have no exactly-once promise.

Permit only one unresolved Send/run per conversation. The daemon enforces this, including two browser tabs racing; UI-disabled Send is not enforcement. Do not admit user follow-ups while busy, stopping, waiting on a decision, or uncertain. There is **no application queue, offline outbox, steering feature, or automatic post-Stop Send** in this slice. OpenCode's own inbox is an admission mechanism, not authorization to expose those product features.

Keep the composer editable through working/disconnected/unavailable states. Retain its draft in volatile presentation memory through ordinary tab navigation/reconnect; do not submit it when connectivity returns. The action surface is Send when eligible and Stop while an operation is active. `42j.4` owns its exact appearance, wording, focus, announcements and draft-reset safeguards.

## Authoritative synchronization and ordering

### OpenCode → daemon

The daemon, not each browser, owns one client event connection plus session log followers for its conversations. Start and consume monitoring before dispatching a first prompt. A detached task must be registered with the daemon service and have an observed success/failure path, not be an unobserved Promise hanging off `Request.signal`.

For a newly owned session, replay `client.experimental.session.log({ sessionID, follow: true })` from the beginning. Fold the supported public durable events into the application's messages/parts, admission receipts and execution state. This is a bounded display/operation projection, **not** a reimplementation of OpenCode's agent loop, model context, database, or permission engine. Owned sessions are created here, not imported/forked legacy sessions requiring an invented history migration.

- Commit the applied exclusive cursor only after reducing its event. Deduplicate by session aggregate/sequence and event ID; retain message ID plus part kind/ordinal or tool-call ID for upserts. Public sequence gaps are legitimate. Durable `*.ended` values **replace** the corresponding preview; never append a final full string to its deltas.
- Treat `log.synced` as completion of replay through its watermark, including any filtered gaps. The service already implements subscribe-before-replay; do not emulate reliable replay with its general event subscription.
- After initial/recovery replay, query `session.get`, `session.active`, pending inbox, session permissions and forms. Reconcile the results with the durable lifecycle and any events received during those queries. Fence each query result by a local synchronization generation and the relevant lifecycle/decision revision; discard/reschedule stale results rather than overwriting a newer terminal or decision. If query lifecycle fields are ahead of the reduced log, take another finite log read to its `log.synced` barrier and bring the follower through that cursor before declaring that lifecycle synchronized. Do not overwrite durable state with an earlier query merely because it arrived last. There is **no verified atomic multi-endpoint snapshot**. Pending-decision queries also need subscribe-before-query event reconciliation and authoritative revalidation on reply; do not mark synchronization healthy until these races are demonstrated by fixtures.
- Busy/idle/retry notifications improve responsiveness but cannot be the only status source. Use matched durable execution facts plus current process-owned active state. An admitted input with no started drain is accepted/not-yet-running, not an assistant failure. Recover pending decisions by stable request IDs and authoritative list/get, not by replaying old popups.
- On durable-log failure, reconnect from the last applied cursor, receive replay and the new watermark, then reconcile queries. Use bounded backoff and generation fencing; do not restart execution. A stream ending changes monitoring health, not the operation's terminal result.

Consume general live events for responsive text/tool previews, deduplicating their event IDs within the live connection generation. Buffer a preview whose durable part-start has not arrived yet; discard it if the canonical full-value end is already known. Do not assume ordering between the live event connection and the independent durable log connection.

On a daemon-to-OpenCode **live preview** gap, retain already observed text but mark affected open previews incomplete. Do not append a newly observed suffix as though it were contiguous with the old prefix. Suppress further incremental display for those parts until a durable full-value `text.ended`/`reasoning.ended` (or authoritative complete part) replaces them. The matched source does not establish replay of an unfinished fragment. Closed output is recoverable from the durable log/history; a current unfinished preview may temporarily say it is catching up. Ordinary **browser** disconnection does not create this gap because the daemon kept consuming and accumulating the previews.

An admitted Send's run records the native execution-start sequence/boundary it belongs to and settles from its corresponding foreground execution terminal, not from one assistant-step end. Foreground execution terminals are not evidence that all background tools/jobs have ended. [OpenCode background completion][background-source] can admit a later synthetic message and wake execution again. Continue observing owned conversations after an initial terminal; correlate subsequent activity to native message/tool IDs, assign a distinct daemon activity/run identity when a new drain has no pending user Send, and never fabricate another user message. A gate must establish the supported tool/background lifecycle and input-to-drain correlation, including a background wake racing a Send. Until then the UI must not claim “all work finished” or global cancellation. No daemon observer may be retired merely because New chat was selected, the last browser disconnected, or an initial foreground response ended.

### Daemon → browser, through Next

Prefer a **single snapshot-first SSE watch**, with short snapshot/receipt queries available for checks. No browser durable event archive or replay-buffer subsystem is required:

1. Under the conversation's serialized state boundary, register the subscriber, capture snapshot revision **R**, and enqueue that snapshot **first**. Enqueue later updates only after it, in revision order. This prevents a read-then-subscribe hole.
2. The snapshot includes conversation ID, daemon epoch, revision, a byte-bounded current message/part manifest window with body references and explicit continuation cursors, run/admission state, preview/synchronization health, pending decisions, and transcript-health metadata supplied by `42j.2`. It is authoritative state and access to full output, not a requirement to inline every content byte in one response.
3. Updates contain absolute message/part descriptors and versioned body references, or explicit state changes keyed by IDs, not unaudited upstream events or unbounded full strings. Within an epoch ignore duplicates/older revisions. An unexpected revision gap, invalid control frame, subscriber overflow, or new epoch requires a replacement snapshot; a large referenced body or failed chunk request does **not**. Never guess the missing text or state.
4. Every reconnect sends a **new authoritative snapshot**, even if the browser sends `Last-Event-ID`. This protocol does not promise browser-event replay. Snapshot replacement, then revision-ordered following, prevents duplicate messages without an unbounded event buffer. Unchanged content retains its generation across snapshots; resnapshotting must not invalidate a usable download or force it to restart.
5. Bound encoded control frames and each subscriber's buffer, with capacity for at least one maximum control frame. Content bytes travel separately in bounded chunks, never through that subscriber buffer. Slow control consumers are disconnected for resync; they cannot block daemon reduction, upstream consumption, transcript work, or other browsers. Stop watching on view departure, but never send execution cancellation. Fence old snapshots/events by conversation ID, epoch and watch generation so late chat A output cannot enter new chat B.

Browser SSE handling must distinguish policy denial from transport loss, recheck state on foreground/refocus, and back off rather than spin. A denied principal stops reconnect attempts until authorization is corrected. `42j.4` must display connection/monitoring health separately from running/completed/failed status and preserve editable text while disconnected.

### Full content without oversized control frames

Use one body-reference/chunk mechanism for user text, assistant text and other displayed variable-length part bodies, in snapshots, updates **and history**. A descriptor identifies the conversation/epoch, message/part key, opaque `contentId`, opaque content `generation`, and committed UTF-8 byte length (`through`); it also distinguishes preview from canonical output. Generations belong to content, not HTTP requests or snapshot revisions. This application contract does not assume that OpenCode offers ranged message reads.

- **Publish before referring:** the daemon makes the referenced bytes readable before committing the descriptor's conversation revision. Growing previews append to a private daemon-owned spill file outside the vault. Within one generation, all committed prefixes are immutable; a later descriptor can increase `through` without changing those earlier bytes. A canonical full-value replacement or any non-prefix correction gets a new generation, made readable before its replacement descriptor is published; retain the finalized byte length and digest for verified rehydration. Never silently change the bytes behind an existing generation/prefix.
- **Bound each transfer step:** the content route returns a validated JSON chunk containing conversation/epoch, content/generation, pinned `through`, requested `offset`, bounded base64 bytes, next offset, and an opaque transfer nonce. Proposed defaults are 64 KiB raw bytes per chunk and 128 KiB maximum encoded chunk response; control/manifest frames have a separate 64 KiB encoded budget. The server chooses chunk length and validates integer offsets and `0 <= offset <= through`, with `through` identifying a published prefix no longer than that generation's committed bytes; requests cannot widen the bound. Every nonfinal successful chunk advances the offset, and completion is exactly the pinned `through`; an unavailable range is an error, not an empty nonfinal chunk. Decode UTF-8 incrementally across chunks, including a multibyte character split at the boundary. Neither JSON encoding nor a single text value can enlarge an SSE frame/subscriber buffer.
- **Pin while reading:** the first chunk request pins that generation/prefix and returns the transfer nonce; subsequent chunks echo it. The nonce is scoped to the authenticated conversation/epoch/content/generation/prefix, is not a credential, and cannot select a file path. Successful chunks renew an idle lease (proposed 60 seconds), so a progressing large transfer is not evicted simply because it exceeds a watch's five-minute lease. Bound concurrent transfers and keep only a small fixed number of chunks in flight. Pinning holds spill-file bytes, not the whole value in RAM. Chunk requests remain independently authenticated short reads with five-second deadlines, no caching, and bounded backoff/retry at the same offset; retries cannot append a chunk twice.
- **Do not chase a moving target:** new revisions do not cancel and restart an in-progress prefix download. Finish the pinned prefix, then extend from its byte offset if the latest descriptor has the same generation and a larger `through`. If the generation changes, retain the already observed old text as superseded/loading while fetching the new generation separately; never concatenate them, and coalesce pending replacement targets rather than starting a download per event. Install completed bytes only when conversation/epoch, content generation and current selection/watch generation still match the accepted descriptor, or as a verified prefix of a later descriptor in that same generation. After watch reconnect, a new snapshot can reaffirm the same content generation/prefix and rebind an existing transfer to the new watch generation without downloading verified bytes again. A late response may populate an old-version cache but cannot overwrite newer canonical text. Download progress does not advance or roll back the conversation revision; it is separate from control synchronization and execution status.
- **Recover without a resnapshot loop:** keep pinned bytes until the transfer's idle lease expires, even if a newer content generation is published. Unpinned finalized bodies may be reclaimed and rehydrated from OpenCode's full projected message, checking the stored byte length and digest before serving that generation again. A missing/expired transfer or unavailable old generation returns a typed content-level error; resolve the current part descriptor through the short manifest read and resume the same immutable prefix when available, or fetch its replacement generation. Do not disconnect the event watch or repeat the same failing snapshot. Current finalized content must have either readable bytes or this verified rehydration path; absence/resource failure is shown explicitly, not as empty text, successful logging, or an infinite retry.

Use ordinary owner-only private spill files and bounded chunk I/O, not an extra content service/framework or a browser content archive. This epoch-scoped runtime cache does not settle vault transcript format or crash durability. Reclaim unpinned superseded previews and verified-rehydratable finalized bodies; expiration must never discard the only recoverable current prefix. This bounds retained transfer/control buffers, not the total size of a conversation. The generated OpenCode client's full-event/JSON decoding can still require value-sized transient allocation, and complete Markdown parsing/rendering can require value-sized browser work. Those costs must be measured by the gate, not described as constant-memory or arbitrary-size support. Browser download/render scheduling may avoid eagerly assembling every old part; inability to parse, spool or render within available resources must surface as a specific resource failure with full source content preserved, not truncation, a new conversation cap, or reconnect churn. This decision specifies correct transfer/recovery; it is not runtime proof or a new rendering feature design.

## Stop, terminal races and partial output

Use these independent state dimensions rather than one overloaded “loading” flag:

- Admission: registered, upstream-unconfirmed, admitted, definitively rejected, or cancelled-before-delivery.
- Operation: accepted, working (including tools/retry/compaction), waiting-for-decision, stop-requested, completed, failed, stopped, or outcome-unknown.
- Monitoring: synchronized, resynchronizing, unavailable, or access-denied; open previews can separately be incomplete.

Stop targets a **specific `runId`**, not “whatever happens to be active when this HTTP request finally arrives.” Serialize Stop and admission in the daemon. Check the target and current native execution boundary before calling the session-wide OpenCode interrupt; a stale Stop must not interrupt a newer Memory Loop Send. The public interrupt API has no execution-ID compare-and-interrupt parameter. The daemon can protect subsequent user commands by holding its admission slot, but cannot promise atomic isolation from an autonomous background continuation starting inside OpenCode; the native cancellation scope is the session's foreground execution. Surface that limit rather than invent a run-scoped native API.

1. Record Stop and publish **stop-requested** immediately. Freeze new admission for that conversation until it settles. Browser disconnection during this request has no cancellation semantics.
2. If Send has not been dispatched, cancel it locally. If upstream admission is uncertain/in flight, keep Stop requested and reconcile that prompt ID first; do not release the slot and allow late admission to run unnoticed.
3. Once admitted, cancel that input's **undelivered inbox item**, then interrupt the target session with resumption disabled. The matched cancel route is a no-op if delivery already won; the interrupt handles the active execution in that race. Do not use `resume: true`, which deliberately resumes some pending work. Observe both calls and the resulting durable log, not just their HTTP statuses.
4. `interrupted: true` acknowledges an interruption request; cleanup/tool settlement is still asynchronous. Confirm the matching durable user interruption and reconciled inactive foreground drain before presenting **stopped**. A confirmed inbox cancellation can instead settle stopped-before-delivery without claiming generation was interrupted.
5. If completion wins before Stop is applied, retain **completed** and explain that it finished before stopping. If interruption returns false, inspect lifecycle/active/inbox state: it can mean idle, already stopping, or terminal settlement. Do not turn an already completed/failed run into stopped, or retry interruption against a newer user run. Preserve a completed target's result even if a racing native continuation was also interrupted. Unresolved transport/cleanup means stop-requested or outcome-unknown, not success.

Keep full admitted user text, all observed partial assistant text, canonical finalized parts, and tool outcomes/partial progress that the service provides. Do not erase or regenerate an interrupted response or treat it as an unsent draft. The [matched step implementation][step-source] flushes fragments and records interrupted tool/assistant failure during cleanup; the [publisher][publisher-source] emits durable full-value text on fragment flush. Verify those behaviors with the actual permitted tool paths before promising preservation beyond what was observed/canonicalized. `42j.2` defines their human-readable transcript representation.

Stop requests cooperative cancellation of OpenCode-owned foreground generation/tools. It cannot undo completed filesystem/network effects or guarantee killing detached subprocesses, remote work, arbitrary plugins or every background descendant. Late confirmed output/effects remain attached to the conversation and monitoring continues. Do not weaken the user's permissive-tool direction to manufacture stronger cancellation guarantees.

## Long-running transport and security

Apply **the existing `allowsWebRequest` policy unchanged** to every Think read, mutation and stream: exact actual Host; supplied Origin must exactly match (including denial of `null`); Fetch Metadata absent/`none`/`same-origin` only; in Tailscale mode exact configured human login and no Funnel marker. No tailnet-wide authorization, wildcard origin, forwarded-Host trust, or local API bypass in Tailscale mode. Require bounded JSON command bodies and fixed method/route schemas, not a general OpenCode RPC/proxy. Commands need this policy just as reads do.

Next constructs fresh service Authorization/Accept/Content-Type as appropriate. It forwards no browser cookies, credentials, Origin, Fetch Metadata, Tailscale identity or forwarding headers. The daemon retains exact Host, constant-time service-token checks, and rejection of browser Origin/`sec-fetch-*`. Replace its global GET-only method restriction with **explicit per-route allowlists** for Think, preserving GET-only Recall and explicit HEAD/OPTIONS rejection. Do not expose either daemon or OpenCode to the browser/LAN/Serve mapping. OpenCode service credentials are distinct from Memory Loop's existing BFF credential and remain daemon-side.

Keep Recall's five-second data-read BFF unchanged. Think command registration and short snapshot/receipt/manifest/chunk calls also have bounded short-response deadlines, but aborting the caller only abandons the response, **not a recorded daemon task**. Each chunk has the same authentication, fixed-target/header projection, response-size bound and five-second deadline; the whole multi-chunk download has no five-second total limit. The new streaming bridge must not use `daemonFetch`'s whole-body buffering or five-second total timeout. Continue using Node's standard HTTP client for daemon requests: the current source documents why Node fetch's injected Fetch Metadata conflicts with the daemon policy.

Proposed streaming defaults to verify on the pinned runtimes: five-second connection/header deadline, heartbeat every 15 seconds, 45-second transport-inactivity deadline, and a five-minute connection lease followed by fresh authenticated snapshot/reconnect. Set Bun/Node/proxy idle settings deliberately above heartbeat intervals. None is a model/run-duration limit. Lease expiry, watcher abort, Next restart, or proxy timeout closes a watch, never calls Stop. Use Hono's maintained SSE support and native Node/Next streaming; no custom Next server or new queue/event framework.

Stream responses are uncached, `no-transform`, `nosniff`, and non-buffered; do not pass arbitrary upstream headers/bodies/errors through. Validate/project application control frames and sanitize pre-stream errors; after headers, close with an application resync/failure indication rather than leaking raw exceptions. Full body bytes use the authenticated, version-pinned chunk path, not an oversized frame or a truncated value. Message/part manifest paging bounds metadata; chunking independently bounds a single valid value. A chunk failure affects content availability, not watch synchronization or the operation's result. Refresh authorization/transport configuration on each new request/lease, consistent with the existing restart semantics for configuration changes.

Log boundary attempts/outcomes and state transitions: command registration/admission, uncertainty, Stop, synchronization generation/reason, stream open/close/overflow, upstream failure and transcript delivery outcomes. Use generated correlation IDs, statuses and safe reason codes; do not log prompt text, tool payloads, raw URLs/headers, credentials, personal locations or OpenCode session contents. Do not route OpenCode stdout/private diagnostics into the browser. Fully permissive tools remain **process-privileged, not vault-sandboxed**; authentication does not isolate this trusted local account or constrain a malicious plugin. `42j.3` must surface that scope and map the requested policy through OpenCode, not bypass it.

## Context, durability and adjacent seams

A conversation can contain many application runs; a run can contain many model/tool steps, retries and compaction. **No Memory Loop conversation-turn or tool-step cap is added.** That does not remove OpenCode's [maximum-step behavior][max-steps], finite provider context/output limits, quotas, or policy constraints. Preserve native compaction/retry/limit outcomes in normalized state. Do not reset to a new conversation automatically when a context limit is reached, and do not substitute the compacted model context for full user/AI history. Verification of effective agent/model limits belongs with `42j.3`; their UI explanation belongs with `42j.4`.

The commitment here is browser-disconnect continuity while the daemon and service live. A Next process restart is only a presentation/watch interruption. A daemon restart loses this layer's resident receipts/previews/monitors; an OpenCode restart can change execution ownership. Reconnection checks the service's reported process identity as well as version; a changed process is not ordinary stream repair, and PID equality alone is not proof that a process never restarted. The matched [service startup][process-source] has its own claim-based restart continuation, but that is not proof of exactly-once effects or an approved Memory Loop crash-recovery design. Do not auto-resend, auto-recreate sessions, infer stopped from service disappearance, or tell the operator that stopping Memory Loop necessarily stopped tools. Surface continuity-unavailable/unknown status. Durable application receipts, automatic reattachment after daemon failure, restart reconciliation, and side-effect recovery need separately approved scope.

Minimal adjacent interfaces:

- **`42j.2` transcript writer:** consumes stable conversation/run/message/tool identities and normalized immutable full-value message changes, tool lifecycle summaries and terminal/interruption facts. It must be able to catch up when no browser exists. Never infer “send not accepted” from a vault-write failure. The snapshot carries logging health separately from execution health. File format/location/write timing, summary redaction, transcript checkpoints and write-failure/restart recovery are that design's decisions; this document chooses none of them.
- **`42j.3` configuration/tool policy:** supplies version-approved service attachment, explicit location, model/agent selection and effective permissions without client-supplied filesystem targets. Owns precedence and startup/plugin compatibility probes. Even with initially permissive settings, pending permissions/forms are real daemon state and must be recoverable; reconnect never auto-approves them. Before replying, revalidate the owned pending request; stale/already-settled decisions trigger resync, not a duplicate or guessed approval.
- **`42j.4` experience:** receives typed admission/run/connection/preview/logging/decision state and stable message keys. Owns accessible role attribution, Markdown/tool presentation, Stop/connection language, responsive layout, draft safeguards and focus/scroll. Preserve the existing branded four-tab shell. This design specifies behavior, not a replacement visual layout or a fake prior-chat control.

## Mandatory capability gate and future validation

Run these **before feature implementation depends on the integration**, using controlled fixtures and recorded evidence. None was executed against OpenCode or the live app for this draft. Network research/package inspection is not integration validation.

First use the pinned public client with injected test-owned HTTP/clock/ID sources. A later authorized real-service probe must isolate HOME/XDG config/data/cache/state, registration, cwd, fixture vault, plugin/provider settings and free loopback ports. No fallback to the user's default service registration, credentials, sessions, plugins or vault is allowed when a fixture selector is absent. Service/model hooks must be inert scripted fixtures or an approved local fake provider—**no real model calls** are needed to establish these contracts. Do not start OpenCode merely to discover what isolation flags mean; verify the exact fixture setup first.

Report the mismatch and obtain an amended version/integration decision. Do not ship a live-stream-only fallback, swap to the embedded SDK, add an application queue, restrict requested tools, or widen the network boundary to make the gate pass.

## Decisions to carry forward, questions and exclusions

Recommend approving: separate-service version-pinned official client; daemon-owned commands/monitoring; three stable IDs with cancelled-command receipts; URL plus one per-tab current-ID pointer; volatile drafts/no follow-up queue; snapshot-first browser watch over the unchanged authenticated BFF boundary; upstream durable replay plus explicitly lossy preview recovery; and request/settlement-aware Stop with preserved partial output.

**Material unresolved product choices:** none additional are required to review this bounded design if those defaults are accepted. Before activation, the user-selected working-directory/configuration context must be settled in `42j.3`; that choice affects which setup/tools/instructions run and must not default accidentally. Transcript failure/durability policy is deliberately left to `42j.2`, and draft-loss safeguards/interaction treatment to `42j.4`. Failed technical capability probes are blockers to report, not product questions disguised as a design decision.

Explicitly excluded: Ground's chat list; user-driven previous-chat selection/resume controls; importing/shared editing of TUI sessions; offline sending/queues/steering; application conversation-turn caps; a new agent/event/queue framework; embedded OpenCode; public or browser-direct OpenCode access; vault transcript format/location; permissive-policy configuration design; detailed Impeccable layout; durable daemon crash recovery; and exactly-once tool side effects. Browser reconnect and current-chat hard reload are **not** exclusions.

No implementation, dependency/configuration changes, service lifecycle actions, vault writes, Beads status changes, commits or acceptance claims accompany this draft. The parent owns fresh design review and canonical tracking.
